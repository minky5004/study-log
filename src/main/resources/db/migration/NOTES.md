# 마이그레이션 파일을 고치기 전에

Flyway 는 `V*.sql` 만 읽으므로 이 파일은 마이그레이션으로 잡히지 않는다. 고칠 수 없는 것을
적어 두는 자리다.

## 적용이 끝난 파일은 주석 한 줄도 고치지 않는다

checksum 이 파일 전체로 계산되기 때문에 주석만 바꿔도 값이 달라진다. 그 파일을 이미 적용한
DB 에서는 부팅의 `validate` 가 불일치를 잡고 앱이 뜨지 않는다.

2026-08-16 에 실제로 물렸다. V1 헤더의 시제를 고쳤더니 checksum 이 `1981831069` 에서
`178111068` 로 옮겨갔고, 운영 배포가 `status 1` 로 죽었다. **로컬에서는 끝까지 초록이었다** —
같은 V1 이 로컬 볼륨에서는 `BASELINE` 타입이라 checksum 자체가 없어 검증 대상이 아니었고,
테스트는 매번 빈 DB 에서 시작해 파일이 곧 정답이었다. 그때 자동화된 경로 중 이 사고를 잡는
것은 하나도 없었다.

지금은 `MigrationChecksumTest` 가 그 자리를 맡는다. 각 `V*.sql` 의 Flyway checksum 을
`src/test/resources/db/migration-checksums.txt` 의 기댓값과 대조하므로, 위와 같은 수정은
커밋 전 `./gradlew test` 에서 걸린다. 파일을 지우거나 이름을 바꾸는 것, 새 마이그레이션을
목록에 적지 않는 것도 같은 테스트가 잡는다.

고쳐야 할 설명이 생기면 파일이 아니라 아래에 적는다.

## V1 헤더의 정오표

- **`baseline-on-migrate` 를 현재형으로 설명하는 대목** — 그 설정은 2026-08-14 에 걷었다.
  08-11 당시 이미 돌고 있던 볼륨 하나가 그 설정으로 버전 1 이 찍혔고, 지금 V1 이 실제로 도는
  곳은 빈 DB 뿐이다.
  - 그래서 **이력표 없는 스키마로 부팅이 막히면 되붙이지 않는다.** `pg_dump` 복원본처럼 스키마는
    찼는데 `flyway_schema_history` 가 없는 DB 를 만나면 그 DB 의 이력부터 본다. 근거는
    `application-prod.properties` 의 Flyway 주석.

## 지금 적용된 것

| 파일 | 운영(Neon) | 로컬 볼륨 |
|---|---|---|
| `V1__baseline_schema.sql` | `SQL` · checksum `1981831069` | `BASELINE` · checksum 없음 |
| `V2__study_plan.sql` | 2026-08-16 배포에서 적용 | `SQL` |

두 DB 의 V1 타입이 다른 것이 위 사고의 원인이고, 그때 로컬이 초록인 것은 근거가 되지
않았다. 지금 V1 의 값이 기댓값 목록에도 있어 로컬 테스트가 운영과 같은 값을 본다.

**기댓값의 정본은 `src/test/resources/db/migration-checksums.txt` 다.** 위 표는 사고의
기록이므로, 새 마이그레이션을 추가할 때 한 줄을 더하는 곳은 그 파일이다.

목록의 값을 고치는 것이 정당한 경우는 아직 어디에도 배포되지 않은 마이그레이션뿐이다.
가드는 배포 여부를 알지 못하므로 그 판단은 사람이 한다.
